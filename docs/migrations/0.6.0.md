# Migration guide: v0.5.0 to v0.6.0

## Who should read this

Projects generated from the 0.5.0 template that are moving to 0.6.0. The
generated `ci.yml` now cancels superseded pull-request runs instead of leaving
the run for the previous head in flight.

Crate source, package metadata and Makefile targets do not change. What changes
is the workflow-level concurrency policy in the rendered CI workflow.

## Impact at a glance

| Priority | Area                         | What to do                                    |
| -------- | ---------------------------- | --------------------------------------------- |
| Review   | Pull-request CI cancellation | Accept the updated `ci.yml` concurrency block |

_Table 1: Obligations when moving from 0.5.0 to 0.6.0._

## 1. Accept the pull-request concurrency block

`ci.yml` now declares a workflow-level concurrency group keyed on the workflow
and the pull-request number, falling back to the ref. `cancel-in-progress` is
enabled only for `pull_request` events, so a new push to a pull request cancels
the run for the previous head, while a dispatch is never cancelled while it
runs. Dispatches on the same ref still share a group, so a newer dispatch can
replace an older pending one.

Copier may report a conflict when it updates an existing `ci.yml`. Resolve it
by keeping the new concurrency block and the project's existing job
customizations; the cancellation policy is independent of the job's steps.

## What does not need to change

- Crate source, package metadata and Makefile targets.
- The coverage publisher (`coverage-main.yml`), which queues rather than
  cancels, and the release and publish workflows, which do not run on pull
  requests.
- `dependabot-automerge.yml`, which triggers on `pull_request_target` rather
  than `pull_request`.

## Migration checklist

- [ ] Accept the `ci.yml` concurrency block when updating the template.
- [ ] Run the generated project's full quality gates after resolving Copier
      conflicts.
